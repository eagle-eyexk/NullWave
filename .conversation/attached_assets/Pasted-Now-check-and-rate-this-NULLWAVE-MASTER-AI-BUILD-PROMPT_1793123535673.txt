# 1. ADVERSARY MODEL AND SECURITY OBJECTIVES

Define the threat model before writing protocol implementation code.

## 1.1 Adversary A — Harvest Now, Decrypt Later

**Identifier:** A_HNDL

The adversary records encrypted messages, handshake material, public keys, and observable metadata today, expecting to acquire more powerful cryptanalytic capabilities in the future.

Objectives:

* Prevent retrospective decryption of recorded messages under the declared post-quantum threat model.
* Limit damage from compromise of long-term identity keys.
* Ensure hybrid key establishment has an explicit security argument.
* Specify which protocol components retain security against quantum-capable adversaries.
* Minimize long-lived plaintext, secret, and ciphertext retention.

Required analysis:

* Classical versus post-quantum assumptions.
* Historical message exposure after long-term key compromise.
* Forward secrecy and post-compromise recovery.
* Key rotation, rekey intervals, and missed-update behavior.
* Backup, device migration, and recovery implications.
* Cryptographic agility and future algorithm migration.

Do not claim HNDL protection solely because ML-KEM appears somewhere in the code.

## 1.2 Adversary B — Malicious Receiver

**Identifier:** A_MAL_RECV

The adversary receives a message and attempts to convince a third party that a particular sender authored it.

The specification must distinguish:

* Message confidentiality.
* Sender authentication during the session.
* Transcript authentication.
* Third-party-verifiable authorship.
* Deniability of a completed conversation.
* Deniability after device compromise.
* Deniability after server compromise.

Define deniability formally using the actual security model of the selected construction.

For every deniability claim, state:

1. The adversary's capabilities.
2. The information available to the adversary.
3. Whether the receiver may be dishonest.
4. Whether the distinguisher is classical or quantum.
5. The required computational or statistical assumptions.
6. What transcript the adversary can produce.
7. What evidence remains available outside the cryptographic protocol.

Do not equate the absence of message signatures with proven deniability.

## 1.3 Adversary C — Honest-but-Curious or Malicious Infrastructure

**Identifier:** A_SERVER

Assume a relay operator can inspect all data stored and transmitted by the server and may correlate:

* Source IP addresses.
* Connection establishment and termination.
* Message arrival times.
* Message sizes.
* Recipient-routing identifiers.
* Delivery acknowledgements.
* Offline polling patterns.
* Group membership events.
* Account and device activity.
* Attachment sizes.
* Retry patterns.

The threat model must separately consider an honest-but-curious server, a compromised server, a malicious server, and colluding servers.

The server must not be trusted for message confidentiality.

The server must not be trusted to enforce identity correctness without client-verifiable evidence.

For the metadata-hardened mode, document the distributed-trust assumptions and the exact information each server can observe.

## 1.4 Additional adversaries

Explicitly address:

* A compromised endpoint.
* Malicious application updates.
* Malicious or compromised dependencies.
* Network attackers.
* Replay and message reordering.
* Denial of service.
* Malicious group members.
* Account takeover.
* Local malware and browser extensions.
* Supply-chain compromise.
* Malicious directory responses.
* Quantum-capable active attackers.
* Server collusion in the two-server mode.

Produce a matrix containing:

# 6. ONE-TO-ONE MESSAGING AND KEY EVOLUTION

Implement a reviewed Double Ratchet or a clearly documented compatible design, with a separate post-quantum update mechanism where the selected protocol supports it.

Do not implement a new ratchet from scratch when a suitable reviewed implementation is available.

## 6.1 Message lifecycle

A message must move through explicit states:

* Composed locally.
* Encrypted locally.
* Queued for delivery.
* Accepted by the transport.
* Stored by the relay.
* Delivered to the recipient device.
* Acknowledged by the recipient.
* Decrypted locally.
* Optionally marked as read.

These states must not be conflated. Server acceptance does not prove recipient delivery.

## 6.2 Message envelope

Define a versioned binary envelope containing only the fields necessary for the protocol.

Specify:

* Protocol version.
* Ciphertext and AEAD tag.
* Nonce handling.
* Key and session identifiers.
* Required associated data.
* Ratchet state references.
* Padding bucket.
* Message sequencing or replay information.
* Delivery-routing token.
* Expiration policy.

Avoid putting cleartext sender identities, contact lists, plaintext content, or unnecessary group membership information in outer envelopes.

The exact field layout must be derived from the selected protocol rather than invented as a cryptographic construction.

## 6.3 Post-quantum updates

Make the update cadence configurable and measurable.

The original candidate of a rekey every \(2^{20}\) records or every 24 hours may be evaluated as an initial policy, but it is not a security proof.

The engineering specification must explain:

* How a fresh secret is generated.
* How it reaches the peer.
* How old and new states coexist during delivery.
* How skipped messages are handled.
* How failed or duplicated updates are handled.
* How state recovery works after compromise.
* How rekeying affects offline devices.
* How old secrets are retired.

Implement tests for replay, message loss, reordering, delayed delivery, duplicated updates, stale state, and simultaneous updates.

## 6.4 Session lifetime

Use an explicit session-expiration policy, configurable by deployment.

A seven-day cap may be a starting policy, but it must not be described as an inherently secure value.

Expired sessions must re-establish cryptographic state through an authenticated protocol, not silently resume with stale keys.

# 8. METADATA-HARDENED TWO-SERVER ROUTING

Implement the Myco research target as a separate subsystem, not as a flag that merely changes API routes.

## 8.1 Architecture

Separate the infrastructure into:

**Writer service**

* Accepts protocol-compliant encrypted writes.
* Performs its assigned oblivious-routing role.
* Cannot decrypt message payloads.
* Does not receive unnecessary read-side state.

**Reader service**

* Provides the assigned oblivious read interface.
* Does not receive unnecessary write-side state.
* Cannot decrypt message payloads.

**Client**

* Implements the validated oblivious protocol.
* Keeps its cryptographic state locally.
* Performs independently specified write and read operations.
* Validates protocol responses.
* Handles server unavailability and state recovery.

The services must be independently deployable and administratively separable.

## 8.2 Trust assumptions

Document the consequences of:

* Writer compromise.
* Reader compromise.
* Writer-reader collusion.
* Network observer.
* Client compromise.
* Malicious server responses.
* Timing correlation.
* IP-address correlation.
* Traffic volume analysis.
* Denial of service.

## 8.3 Modes

Implement clearly labeled privacy modes:

**Baseline mode**

* End-to-end encryption.
* Minimum necessary relay metadata.
* Standard delivery behavior.

**Enhanced metadata mode**

* Reduce cleartext routing information.
* Apply suitable padding.
* Reduce unnecessary identifiers and logging.

**Metadata-hardened mode**

* Use the validated two-server oblivious construction.
* Require both roles.
* Fail closed with respect to the advertised privacy guarantee if required services or protocol prerequisites are unavailable.
* Never silently fall back to baseline mode while retaining a metadata-hardened label.
