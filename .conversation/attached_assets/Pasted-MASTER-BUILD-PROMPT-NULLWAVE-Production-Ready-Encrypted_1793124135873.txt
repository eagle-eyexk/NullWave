8. CRYPTOGRAPHY AND SECURITY REQUIREMENTS

This section is mandatory.

A visually convincing encryption interface is not sufficient. The security model must be documented, implemented, and tested.

A. Cryptographic architecture

Use established, maintained cryptographic libraries and published protocols. Do not invent custom encryption algorithms.

If Rust is the backend language, keep security-critical server functionality in Rust where appropriate.

Use WebAssembly for browser-side cryptographic operations only when the selected libraries, platform support, and implementation architecture justify it.

Choose a documented end-to-end encryption protocol suitable for the application’s requirements, including multi-device and group messaging where supported.

Document:

* Identity keys.
* Session establishment.
* Message encryption and authentication.
* Key rotation.
* Replay protection.
* Forward secrecy properties.
* Device addition and removal.
* Group membership changes.
* Recovery limitations.
* Threat model and out-of-scope threats.

Use post-quantum or hybrid key establishment only with recognized, maintained implementations and a documented protocol design. Do not claim that a particular algorithm makes the entire product quantum-proof.

B. Key handling

* Generate keys using cryptographically secure randomness.
* Keep private keys under client control where the threat model requires it.
* Use platform-supported secure storage when available.
* Never expose private keys through logs, analytics, error messages, or debugging endpoints.
* Prevent secrets from entering URLs.
* Avoid plaintext messages in persistent browser storage unless explicitly justified and protected by the documented threat model.
* Implement key replacement and revocation behavior.
* Handle device loss and account recovery honestly.
* Avoid creating a centralized decryption capability that contradicts the product’s security promises.

C. Transport and server security

Use TLS for network communications.

Apply:

* Authorization checks on every protected resource.
* Strict session management.
* Input validation.
* Rate limiting.
* Secure secret management.
* Appropriate security headers.
* Origin and cross-site request protections.
* Dependency auditing.
* Structured security logging without sensitive message content.
* Safe error handling.
* Database access controls.
* Protection against injection and unauthorized object access.

The server should handle ciphertext rather than plaintext for end-to-end encrypted messages, except for explicitly documented features that require different treatment.

Do not claim that metadata is eliminated if the server still processes account identifiers, IP addresses, timestamps, delivery information, or other operational metadata.

D. Honest security states

The interface must distinguish between:

* Encrypted in transit.
* End-to-end encrypted.
* Contact identity verified.
* Device trusted.
* Session expired.
* Verification required.
* Encryption unavailable.
* Security warning.

These states are not interchangeable.

If encryption is not initialized or a cryptographic operation fails, do not silently fall back to plaintext while showing a secure indicator.

If a secure messaging feature is not implemented, mark it as unavailable or under development rather than simulating success.

9. BACKEND, DATABASE, AND REAL-TIME MESSAGING

Build the actual application architecture, not just the frontend.

Use the existing repository’s stack if one exists. Otherwise, choose a maintainable architecture such as:

* Frontend: React with TypeScript and a suitable modern framework.
* Styling: Tailwind CSS or an equivalent reusable styling system.
* Backend: Rust using a maintained web framework such as Axum.
* Database: PostgreSQL.
* Real-time delivery: WebSockets or another suitable authenticated transport.
* Cryptography: Established, maintained cryptographic libraries selected for the documented protocol.
* Testing: Unit, integration, end-to-end, and security-focused tests.

Do not add every technology simply because it appears in this list. Make the stack coherent, explain key choices, and pin compatible dependency versions.

Implement real backend flows for:

* Account creation and authentication.
* User profiles.
* Contact discovery according to the privacy model.
* Conversations and group membership.
* Encrypted message submission.
* Authenticated message delivery.
* Message persistence according to the retention policy.
* Device registration and revocation.
* Notifications where supported.
* Connection status and reconnect behavior.

Use database migrations, indexes, validation, and transaction handling where appropriate.

Protect conversation history and attachment access with explicit authorization checks. A user must not access another user’s conversations by changing an identifier in a request.

WebSocket connections must be authenticated and authorized. Recheck access when membership or session status changes.

Implement reconnection, retry, duplicate prevention, and delivery acknowledgments where applicable.

Do not pretend that multi-device synchronization is secure merely because the same account can sign in on multiple devices.
